Gnadenlos

CVE-2026-98432

No grace period. No mercy.
The vulnerability your kernel has carried in its heart since 2016.

What hath happened?

In the Linux kernel’s IPv4 TCP handshake, a request socket’s IP options (inet_opt, ireq_opt) are freed without waiting for the RCU grace period to end. When a SYN-ACK retransmit and the request socket’s migration run at the same time, a code path reaches into memory that has already been freed. A classic use-after-free, triggered over the network, no authentication required.

Best case: kernel panic. Worst case: root code execution, demonstrated under lab conditions. The kernel simply forgot to show mercy – and we turned it into a brand.

Regular IPv6 connections are not affected in the same way; a separate fix has been announced for a related IPv6 edge case.

How fares our salvation?

As of November 5, 2026

On November 3, Ubuntu raised its priority from High to Critical. There is still no patch in the regular -updates pocket for the LTS releases, though: the Ubuntu tracker still lists 22.04, 24.04 and 26.04 as “Vulnerable”, with fixed kernels in progress. No Ubuntu Security Notice has been published yet. Critical enough to upgrade the rating, not critical enough to ship. A theologically interesting state.

The fixed kernels (5.15.0-203, 6.8.0-149, 7.0.0-43) have been sitting in -proposed since October 26 and 27. Canonical is still testing them on more than 2,000 certified systems and explicitly addresses people who run their own kernel acceptance tests. For everyone else, -proposed in production is a leap of faith for the adventurous. If you want to jump, the steps are in the Canonical blog. Ubuntu 26.10 already has 7.3.0-10.10 in -updates; for 20.04 and older, the fix is still pending.

Other distributions are further along: Debian, RHEL 8 to 10, AlmaLinux, Oracle Linux, Amazon Linux and SLES 15 SP7/16 already ship fixed kernels.

The apocalypse is running late. As far as we know, the whole internet has not been rooted yet. Anthropic has not published its exploit, and the CVE was not in CISA’s KEV catalog as of November 4. Since November 2 and 3, however, suspected scanning on port 443 over MPTCP has been observed, and the first race triggers and DoS PoCs are showing up on GitHub. The horsemen aren’t here yet, but you can hear hooves.

Am I damned?

Fixed upstream in 5.10.272, 5.15.223, 6.1.190, 6.6.159, 6.12.113, 6.18.56, 7.2.10 and 7.3. Introduced in kernel 4.4. The check also recognizes Ubuntu’s -generic kernels. If your server falls in between, start praying.

Distributions backport fixes into kernels whose version number doesn’t reveal it. Your distribution’s security tracker is authoritative.

uname -r
# Ubuntu / Debian: does the installed package contain the fix?
apt changelog linux-image-$(uname -r) 2>/dev/null | grep -m1 CVE-2026-98432
# Is the patched kernel actually running?
sudo needrestart -k
# Proxmox VE
pveversion -v | grep -E 'proxmox-kernel|pve-kernel'

Exorcism to go

The attacker needs IPv4 options (Record Route or Timestamp) in the SYN. Legitimate TCP traffic practically never carries IPv4 options; TCP options such as timestamps and window scaling are a different thing and stay untouched, as does IPv6. The rule therefore drops incoming IPv4 TCP packets whose IP header is longer than 20 bytes. Red Hat and Ubuntu agree: this reduces the risk but does not fully prevent exploitation. An exorcism, not a miracle.

nftables

sudo nft -f - <<'EOF'
table ip cve_2026_98432 {
  chain prerouting {
    type filter hook prerouting priority -300; policy accept;
    meta l4proto tcp ip hdrlength > 5 counter drop
  }
}
EOF
sudo nft list table ip cve_2026_98432   # counter shows drops
# remove (after rebooting into a fixed kernel)
sudo nft delete table ip cve_2026_98432

iptables (raw table, before connection tracking)

sudo iptables -t raw -I PREROUTING -p tcp -m u32 --u32 '0>>24&0x0f=6:15' \
  -m comment --comment CVE-2026-98432 -j DROP
sudo iptables -t raw -L PREROUTING -n -v   # counter shows drops
# remove
sudo iptables -t raw -D PREROUTING -p tcp -m u32 --u32 '0>>24&0x0f=6:15' \
  -m comment --comment CVE-2026-98432 -j DROP

Both rules hook prerouting, so they also catch packets the host routes on to containers. Bridged traffic between containers on the same host bypasses them, and containers with their own network namespace need the rule applied separately. Neither rule survives a reboot: if you restart into an unpatched kernel, apply it again.

The u32 match is missing from RHEL 9 and 10 kernels; use nft there. Don’t use it where CIPSO labels are in use, because they travel in exactly those IPv4 options. A separate nft table is left alone by iptables-restore, ufw and firewall managers that only manage iptables rules.

Frequently Asked Lamentations

Does a use-after-free really need its own website?

Heartbleed had one. We are worth no less.

Why “Gnadenlos”?

German for “merciless”, literally “without grace”. The kernel frees memory before the RCU grace period – in German, the Gnadenfrist – has expired. No grace period, no grace. It took us three meetings.

Is there a hymn?

O sacred head, now wounded, your options freed too soon, no grace period was granted, the pointer points at doom.

Can’t I just lock down the firewall?

Fully locked down only if you want a very expensive paperweight. The exorcism above is more targeted: it only casts out packets carrying IPv4 options. Salvation still only comes with a reboot into a fixed kernel.

Can I show this page to my auditor?

Better not. Show them kernel versions, patch dates and proof of reboot. Auditors have no sense of humour, but they do have checklists.
