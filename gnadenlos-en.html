Gnadenlos

CVE-2026-98432 · Linux kernel, IPv4 TCP

No grace period, no mercy.

9.8CVSS 3.1 in the CVE record
CriticalUbuntu priority since November 3
since 4.4present in the kernel

What it is

In the IPv4 TCP handshake, the kernel frees a request socket’s IP options (inet_opt, ireq_opt) without waiting for the RCU grace period to end. When a SYN-ACK retransmit and the migration of the request socket run concurrently, one code path can access memory that has already been freed.

It can be triggered over the network without authentication. At minimum, the result is a kernel crash; under specific conditions, remote code execution as root has been demonstrated.

Regular IPv6 connections are not affected in the same way. A separate fix has been announced for a related IPv6 edge case.

Current status

As of November 5, 2026

On November 3, Ubuntu raised its priority from High to Critical. There is still no patch in the regular -updates pocket for the LTS releases, though: the Ubuntu tracker still lists 22.04, 24.04 and 26.04 as “Vulnerable”, with fixed kernels in progress. No Ubuntu Security Notice has been published yet.

The fixed kernels (5.15.0-203, 6.8.0-149, 7.0.0-43) have been sitting in -proposed since October 26 and 27. Canonical is still testing them on more than 2,000 certified systems and explicitly addresses people who run their own kernel acceptance tests. For production systems, that’s one for the adventurous. If you want it anyway, the steps are in the Canonical blog. Ubuntu 26.10 already has 7.3.0-10.10 in -updates; for 20.04 and older, the fix is still pending.

Other distributions are further along: Debian, RHEL 8 to 10, AlmaLinux, Oracle Linux, Amazon Linux and SLES 15 SP7/16 already ship fixed kernels.

Exploitation. As far as we know, the whole internet has not been rooted yet. Anthropic has not published its exploit, and the CVE was not in CISA’s KEV catalog as of November 4. Since November 2 and 3, however, suspected scanning on port 443 over MPTCP has been observed, and the first race triggers and DoS PoCs are showing up on GitHub. The window for relaxed waiting is getting smaller.

Am I affected?

Fixed upstream in 5.10.272, 5.15.223, 6.1.190, 6.6.159, 6.12.113, 6.18.56, 7.2.10 and 7.3. Introduced in kernel 4.4. The check also recognizes Ubuntu’s -generic kernels.

Distributions backport fixes into kernels whose version number doesn’t reveal it. Your distribution’s security tracker is authoritative.

uname -r
# Ubuntu / Debian: does the installed package contain the fix?
apt changelog linux-image-$(uname -r) 2>/dev/null | grep -m1 CVE-2026-98432
# Is the patched kernel actually running?
sudo needrestart -k
# Proxmox VE
pveversion -v | grep -E 'proxmox-kernel|pve-kernel'

Mitigation until you can patch

The attacker needs IPv4 options (Record Route or Timestamp) in the SYN. Legitimate TCP traffic practically never carries IPv4 options; TCP options such as timestamps and window scaling are a different thing and stay untouched, as does IPv6. The rule therefore drops incoming IPv4 TCP packets whose IP header is longer than 20 bytes. Red Hat and Ubuntu agree: this reduces the risk but does not fully prevent exploitation.

nftables

sudo nft -f - <<'EOF'
table ip cve_2026_98432 {
  chain prerouting {
    type filter hook prerouting priority -300; policy accept;
    meta l4proto tcp ip hdrlength > 5 counter drop
  }
}
EOF
sudo nft list table ip cve_2026_98432   # counter shows drops
# remove (after rebooting into a fixed kernel)
sudo nft delete table ip cve_2026_98432

iptables (raw table, before connection tracking)

sudo iptables -t raw -I PREROUTING -p tcp -m u32 --u32 '0>>24&0x0f=6:15' \
  -m comment --comment CVE-2026-98432 -j DROP
sudo iptables -t raw -L PREROUTING -n -v   # counter shows drops
# remove
sudo iptables -t raw -D PREROUTING -p tcp -m u32 --u32 '0>>24&0x0f=6:15' \
  -m comment --comment CVE-2026-98432 -j DROP

Both rules hook prerouting, so they also catch packets the host routes on to containers. Bridged traffic between containers on the same host bypasses them, and containers with their own network namespace need the rule applied separately. Neither rule survives a reboot: if you restart into an unpatched kernel, apply it again.

The u32 match is missing from RHEL 9 and 10 kernels; use nft there. Don’t use it where CIPSO labels are in use, because they travel in exactly those IPv4 options. A separate nft table is left alone by iptables-restore, ufw and firewall managers that only manage iptables rules.

Questions

Why “Gnadenlos”?

It’s German for “merciless”, and literally “without grace”. The RCU grace period – in German, the Gnadenfrist – is how long memory must wait before it’s freed, until no reader holds it anymore. Here, it gets skipped.

Does a firewall help?

A regular port firewall hardly does: every service accepting TCP over IPv4 is attack surface. The targeted rule against IPv4 options above reduces the risk considerably, but it doesn’t replace the kernel update and reboot.

What should go into the documentation?

Affected systems, the running kernel version before and after the update, the patch date and proof of reboot; until then, where the mitigation is active, including its counter. Live patching only replaces that proof if the livepatch explicitly covers this CVE.

Patch, reboot, verify.
