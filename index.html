Gnadenlos

CVE-2026-98432 · Linux-Kernel, IPv4 TCP

Keine Grace-Period, keine Gnade.

9.8CVSS 3.1 im CVE-Record
CriticalUbuntu-Priorität seit 3. November
seit 4.4im Kernel enthalten

Worum es geht

Im IPv4-TCP-Handshake gibt der Kernel die IP-Optionen einer Request-Socket (inet_opt, ireq_opt) frei, ohne das Ende der RCU-Grace-Period abzuwarten. Laufen SYN-ACK-Retransmit und die Migration der Request-Socket parallel, kann ein Codepfad auf bereits freigegebenen Speicher zugreifen.

Auslösbar über das Netzwerk, ohne Authentifizierung. Die Folge ist mindestens ein Kernel-Crash; unter bestimmten Bedingungen wurde Codeausführung mit Root-Rechten demonstriert.

Normale IPv6-Verbindungen sind nicht auf dieselbe Weise betroffen. Für einen verwandten IPv6-Sonderfall ist ein separater Fix angekündigt.

Die gefixten Kernel (5.15.0-203, 6.8.0-149, 7.0.0-43) liegen seit dem 26. und 27. Oktober in -proposed. Canonical testet sie dort noch auf über 2.000 zertifizierten Systemen und richtet sich ausdrücklich an alle, die eigene Kernel-Abnahmetests fahren. Ausnutzung. Soweit bekannt, ist noch nicht das ganze Internet gerootet. Anthropic hat seinen Exploit nicht veröffentlicht, und im KEV-Katalog der CISA stand die CVE am 4. November nicht. Seit dem 2. und 3. November wird allerdings mutmaßliches Scanning auf Port 443 über MPTCP beobachtet, und auf GitHub tauchen erste Race-Trigger und DoS-PoCs auf. Das Zeitfenster für entspanntes Abwarten wird kleiner.

Mitigation bis zum Patch

Der Angreifer braucht IPv4-Optionen (Record Route oder Timestamp) im SYN. Legitimer TCP-Verkehr trägt praktisch nie IPv4-Optionen; TCP-Optionen wie Timestamps und Window Scaling sind etwas anderes und bleiben unberührt, ebenso IPv6. Die Regel verwirft deshalb eingehende IPv4-TCP-Pakete, deren IP-Header länger als 20 Byte ist. Red Hat und Ubuntu sind sich einig: Das senkt das Risiko, verhindert die Ausnutzung aber nicht vollständig.

nftables

sudo nft -f - <<'EOF'
table ip cve_2026_98432 {
  chain prerouting {
    type filter hook prerouting priority -300; policy accept;
    meta l4proto tcp ip hdrlength > 5 counter drop
  }
}
EOF
sudo nft list table ip cve_2026_98432   # Counter zeigt Drops
# entfernen (nach Reboot in gefixten Kernel)
sudo nft delete table ip cve_2026_98432

iptables (raw-Tabelle, vor Connection Tracking)

sudo iptables -t raw -I PREROUTING -p tcp -m u32 --u32 '0>>24&0x0f=6:15' \
  -m comment --comment CVE-2026-98432 -j DROP
sudo iptables -t raw -L PREROUTING -n -v   # Counter zeigt Drops
# entfernen
sudo iptables -t raw -D PREROUTING -p tcp -m u32 --u32 '0>>24&0x0f=6:15' \
  -m comment --comment CVE-2026-98432 -j DROP

Beide Regeln hängen an prerouting und erfassen damit auch Pakete, die der Host an Container weiterroutet. Gebridgter Verkehr zwischen Containern auf demselben Host läuft vorbei, und Container mit eigenem Netzwerk-Namespace brauchen die Regel separat. Keine der Regeln überlebt einen Reboot: Wer in einen ungepatchten Kernel neu startet, muss sie erneut setzen.

Das u32-Match fehlt in den Kerneln von RHEL 9 und 10, dort nur nft verwenden. Nicht einsetzen, wo CIPSO-Labels genutzt werden, die stecken nämlich genau in IPv4-Optionen. Eine eigene nft-Tabelle wird von iptables-restore, ufw oder Firewall-Managern, die nur die iptables-Regeln verwalten, nicht angefasst.

Fragen

Warum „Gnadenlos“?

Die RCU-Grace-Period ist die Gnadenfrist, die freizugebender Speicher abwarten muss, bis kein Leser ihn mehr hält. Hier wird sie übersprungen.

Hilft eine Firewall?

Eine normale Port-Firewall kaum: Jeder Dienst, der TCP über IPv4 annimmt, ist Angriffsfläche. Die gezielte Regel gegen IPv4-Optionen oben senkt das Risiko deutlich, ersetzt aber nicht das Kernel-Update mit Reboot.

Was gehört in die Dokumentation?

Betroffene Systeme, laufende Kernel-Version vor und nach dem Update, Patch-Datum und Reboot-Nachweis; bis dahin, wo die Mitigation aktiv ist, samt Counter-Stand. Live-Patching ersetzt den Nachweis nur, wenn der Livepatch diese CVE ausdrücklich abdeckt.

Patchen, neu starten, prüfen.
